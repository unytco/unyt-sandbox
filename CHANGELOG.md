## [Unreleased]

### Added

- **Release pipeline: a post-release smoke of every shipped artifact (UNYT-966/967/968), in two phases.** New `scripts/smoke/`, runnable locally with Docker (`scripts/smoke/run-smoke.sh <artifact>`).
  - **Phase 1, "does it open" — the phase that fails the release run.** Each installer the release carries is installed on a runner, launched, and photographed: the `.deb`, the AppImage, both `.dmg`s, the NSIS `.exe` on windows-2022 and windows-2025, and the `.msi` on windows-2025. **What a green lane asserts:** the artifact installed, the app reached a healthy backend state, and a frame captured from *the app's own window* is dominated by a colour the app declares with content drawn on it (≥1000 distinct colours, ≤75% dominant — bars a bare menu bar cannot clear). Every lane first photographs the screen *before* launching and reports `UNTRUSTED` if that frame already passes for the app. **What it does not assert:** that the screen is the *right* screen — no text is read and no element is identified. macOS can answer `WINDOW-ONLY` (the app launched and put a real on-screen window up at a real size; webview paint unverified), which is green with a warning and never the word a photographed lane gets. A lane that cannot launch or cannot trust its capture goes red; it never skips and is never quietly green. `scripts/smoke/load-proving/`.
  - **Phase 2, "static checks" — advisory on a release, red on a hand dispatch.** What the artifact *is*: install, version, binary-compatibility and declared-dependency checks in pristine distro containers; the macOS signing, notarization, architecture and deployment-target set; a Windows silent install/uninstall cycle with an import-table check.
  - **The phases run concurrently**, so a notarization finding still lands on a build whose window came up blank.
  - **A lane that does not answer is red on every platform.** Each phase-1 lane reads its verdict in a step of its own that runs whatever the launch did, so a launch that never happened leaves no verdict and no exit code, and both read as NO ANSWER.
  - **An installer the inventory cannot name fails the run.** The presence tests are exact suffixes, so a renamed artifact used to read as an absent one and its lane would quietly stop existing; anything installer-shaped that no suffix claims is now an error naming the asset.
  - **Not covered by either phase, and still a hand check** ([`docs/windows-clean-machine-check.md`](docs/windows-clean-machine-check.md)): a machine that is not a CI runner — SmartScreen's "unknown publisher" block, a missing WebView2 runtime, a missing Visual C++ redistributable.
  - **Two findings, both gated red:** the `.deb` declared 2 of its 11 shared libraries (fixed in `unyt/`), and the Windows installers are unsigned, so users meet a SmartScreen "unknown publisher" block.
- **Release pipeline: tag-derived release kinds + `.happ` inheritance (release-patterns UNYT-948).** `vM.m.0` builds the DNA; `vM.m.p` inherits it and repacks only the UI.
- **Release pipeline: a version contract (release-patterns UNYT-946).** `unyt/src-tauri/Cargo.toml` is the single source of truth for the version; a pushed tag or a `tauri.conf.json` that disagrees fails the release before any artifact is built (new `scripts/check-version-contract.sh`). The shipped app build now receives `VITE_MIGRATION_SERVICE_URL` (the update router the app polls), with a guard step that fails an empty value — no more installers that can never check for updates.

### Changed

- **Release pipeline: the pre-release tag channel is `-dev.*`, not `-rc.*`.** The update router matches `vM.m.p` only, so no pre-release tag is offered to users as an update.
- **Release pipeline: a pre-release build's MSI product version is derived from the tag (new `scripts/msi-version.sh`).** `0.101.0-dev.3` yields `0.101.0.3`, written at build time — committed, a `wix.version` would outlive its release.
- **Release smoke: an artifact is checked against its own version**, pre-release suffix included, and the `.msi` against the four-field version Windows registers.
- **Release smoke: the inventory matches asset suffixes literally, and every result row is vetted.** Two fields, a declared name, a verdict of `pass`, `warn` or `FAIL`; anything else reads `MALFORMED`.
- **Release smoke: the Windows lane summarises only the installers the release carries.** A skipped installer says so in the published table, and a lane that smoked neither installer fails.
- **Release smoke: the Windows uninstall check reads the install directory before it runs the uninstaller.** Missing state fails the check with the app still on disk to re-run against.
- **Release pipeline: the Linux build leg reports free disk either side of the build.** A release compile of the Holochain 0.7 stack is large enough to exhaust a runner.
- **Release pipeline: a pushed tag is never interpolated into a shell.** The changelog step takes the version through `env`; tag names are untrusted input.
- **Release pipeline: the release build installs with `yarn install --frozen-lockfile --ignore-engines`.** Both the build path and the UI-release path, matching the app's other CI.
- **Release pipeline: a release run fails when the app does not open, or when the smoke cannot prove its own checks still fail.** The `static-checks-advisory` input softens phase 2 alone — it annotates and reports a static failure without failing the release run — and there is no switch that can reach phase 1 or the setup job that runs the check-regression oracle. So a red phase-1 lane, a regressed oracle, and a release whose asset list cannot be read all fail the run; a red static check does not. A hand-dispatched smoke answers red for everything, as before. Nothing publishes the release either way: it is created draft, a human publishes it, and the run's colour is what they read first.
- **Release pipeline: publish only artifacts the repo builds.** Drop the never-built `agent_details.dna` from the release, and set `artifactErrorsFailBuild` so a declared-but-missing artifact fails the release. The matrix job takes the version from the `publish-happ` job output instead of re-reading `tauri.conf.json`.
- **Release smoke: the `ui_ready` webview gate is gone — it could never pass.** The breadcrumb is emitted by `app-root`, which lives in the main window, and that window is created by `post_conductor_ready` only once the conductor is serving; a cold install on an authenticated build stops at `HcAuthRequired`, which deliberately does not reach `LairReady`, so setup never runs and the window never opens. The gate failed on every release it ran against while the app was working correctly. **Phase 2's container launch check proves the backend only** — that the process comes up, reaches a healthy state, is a cold install, stays up and shuts down cleanly. What the webview drew is phase 1's question, answered by photographing the app's own window on a runner with a display rather than by a log line.
- **Release smoke: the macOS gate images are pinned, and the build deliberately is not.** Every macOS lane of both phases runs on `macos-15` / `macos-15-intel` — the images the launch lanes were proven on — because `macos-latest` has meant macOS 26 since mid-2026 and its screen-capture rules differ, so a rolling gate would change what "proven" means with no commit to point at. The build legs keep `macos-latest`, unchanged: **the artifact is built on a newer macOS than it is installed and launched on**, which is the useful direction, since it asks whether the build runs on an OS older than the one that produced it. `test-oracle.sh` holds both halves — a gate off the proven set fails, and so does a pinned build leg, so changing what users install stays a decision of its own.
- **Release smoke: Stage 3 reads as tests, and its name stops repeating on every line.** GitHub prefixes each called job with the caller's, so `Stage 3 - does it open, and the static checks` sat in front of all 16 checks and pushed the part that differs off the end. The caller is now `Stage 3` and each lane names itself: `setup test`, `test opens app — <target>`, `test static checks — <target>`. Phase numbers are gone from the names: everything after the setup runs concurrently, so they implied an order that was never there. The phases themselves are unchanged and `static-checks-advisory` still reaches phase 2 alone. `test-oracle.sh` now holds every lane's name to the phase its id declares, and resolves each matrixed lane's rows to check they render distinct names — so a blocking lane cannot sit under the advisory phase's name, and two Windows rows cannot arrive in the Checks list under one.
- **`AGENTS.md` is one line: read the code.** The release scripts, the harnesses that test them and the workflows that run them are the only accurate account of this repo, and a second one in prose only drifted from them.

### Fixed

- **Release smoke: the dependency check called a correctly-floored package under-declared.** tauri-bundler copies `Depends:` verbatim from `tauri.conf.json` and then appends bare, unversioned `libwebkit2gtk-4.1-0` and `libgtk-3-0` entries of its own, so the shipped `.deb` names those two packages twice — once with a floor, once without. Sorting the list put the bare entry first (a prefix sorts before its extension) and `smoke_depends_gaps` matched only the first entry per package name, so it read the bare one and reported `UNCONSTRAINED` against a package whose floor was there all along; red on all four images in `v0.101.0-dev.1`. Debian `Depends` is a comma-separated AND list, so a duplicate entry adds a requirement rather than replacing one — verified against apt and dpkg on ubuntu:22.04 and debian:13, which refuse an unsatisfiable floor in either order. Every declared entry for a name is now weighed and the strongest lower bound decides, so ordering cannot change the verdict; a package with no adequate floor anywhere is still `UNCONSTRAINED`, and two too-low floors still report `TOOLOW` naming the higher. The failure message no longer claims the bundler "never computes one" — it says what the bundler actually appends, which is what would otherwise send a reader to add floors that already exist.
- **Release smoke: a declared alternation handed one package's version floor to another.** The constraint parser read "the first `(…)` on the line" and credited it to the line's first package name, so `libgtk-3-0 | libgtk-3-0t64 (>= 3.21.5)` counted as a floor on `libgtk-3-0` — which apt may satisfy with an unversioned `libgtk-3-0`, applying no floor at all. Weighing every declared entry would have widened this from a latent false pass into a live one, by removing the accidental red that a bare duplicate happened to be providing. An alternation is now only as strong as its weakest branch: every branch must carry an adequate floor, and a branch naming a package outside the dependency's alias set counts as no floor, because it can satisfy the whole line on its own. Two further guards alongside it: a computed constraint with no version (`libfoo (>=)`) is reported as unreadable rather than treated as nothing to prove, since `dpkg --compare-versions X ge ''` is true for every `X`; and `dpkg` itself joins the tool preflight, because every comparison runs through it with stderr discarded and a `dpkg` that cannot run reported each correct floor as malformed.
- **Release smoke: the expected-dependency snapshots were a pre-0.7 baseline.** All four `scripts/smoke/expected-deb-depends.*.txt` were captured from `v0.100.0`, so the drift gate fired on the first Holochain 0.7 release, on every image. The drift is the same two entries everywhere — `libcairo-gobject2` and `libpango-1.0-0` — because it is a property of the ELF, not of the resolving distro: `v0.100.0`'s binary carried `DT_NEEDED` entries for both while importing not one symbol from either, and `ldd -u` named exactly those two as its unused direct dependencies. The 0.7 build no longer over-links them, GTK still requires both at higher floors than the snapshots recorded, and all four images still install them. Re-captured from `v0.101.0-dev.1`, with the provenance header updated and the reasoning recorded alongside it.
- **Release smoke: the macOS check harness worked in the release's own state and results files.** `run_scenario` gave the real `check-macos.sh` a stub toolchain but no state directory of its own, so under the workflow's environment — which sets `UNYT_SMOKE_STATE` and `UNYT_SMOKE_RESULTS` before the harness step — every scenario mounted into one shared directory, the scenario whose image holds no `.app` passed nine checks against the bundle the previous one had extracted, and 48 fixture rows landed in the results file the release's real checks report from, where a duplicate row reads as "a check is wired up twice". A bare local run hid both: with the variable unset the script mints a temp directory per invocation. Every invocation now gets its own state and results files, the harness puts itself in CI's shape whatever the environment it is run from, and a seeded caller directory is checked at the end to prove nothing reached it.
- **Release smoke: the Linux lane starts on a runner with no cached image.** `docker run`'s stderr was folded into its stdout, so the pull narration became the container id and every later `docker exec` failed — which the reaping probe then reported as "PID 1 is not reaping orphans". The stderr is captured to the lane instead, and a genuine docker failure still prints it.
